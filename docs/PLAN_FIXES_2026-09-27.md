### Шаг 1.5 — Исправить relationship Category (проблема №5)

**Файл:** `src/server/models.py`, класс `Category`.

**Что делать:** заменить
```python
children = relationship("Category", backref="parent", remote_side=[id])
```
на
```python
parent = relationship("Category", backref="children", remote_side=[id])
```

**Почему:** текущая запись с `remote_side=[id]` — many-to-one, атрибут
`children` фактически возвращает родителя. Код пока не использует эти
атрибуты, поэтому замена безопасна; но любой будущий код сломался бы.

**Проверка:** сервер стартует без ошибок; `GET /api/categories/tree`
возвращает то же дерево, что и раньше (роут строит дерево вручную, не через
relationship).

## Этап 2. Надёжность данных и БД

### Шаг 2.1 — SQLite: WAL + busy_timeout (проблема №13)

**Файл:** `src/server/database.py`.

**Что делать:**
```python
from sqlalchemy import event

engine = create_engine(
    DATABASE_URL,
    connect_args={"check_same_thread": False, "timeout": 30},
)

@event.listens_for(engine, "connect")
def _set_sqlite_pragma(dbapi_connection, connection_record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA journal_mode=WAL")
    cursor.execute("PRAGMA busy_timeout=30000")
    cursor.close()
```

**Почему:** фоновые сканы (scheduler, потоки) + HTTP-запросы параллельно →
`database is locked` без ожидания. WAL даёт конкурентное чтение, таймаут —
ретрай вместо мгновенной ошибки.

**Проверка:** запустить скан каталога и параллельно гонять `GET /api/products`
— ошибок блокировки быть не должно.

---

### Шаг 2.2 — Миграции: честная регистрация (проблема №12)

**Файл:** `src/server/database.py`.

**Что делать:**
1. Каждая миграция-функция возвращает `bool` (успех) или бросает исключение;
   подавляющие `except: pass` внутри — заменить на логирование и возврат `False`.
2. `_run_migration` регистрирует миграцию в `schema_migrations` **только**
   при успехе; при провале — warning в лог и НЕ регистрировать (следующий
   старт повторит попытку).
3. Перевести `print()` на `logger` (заодно проблема №19).

**Почему:** сейчас миграция с внутренне подавленной ошибкой регистрируется
как выполненная — частично применённая схема замораживается навсегда.

**Проверка:** удалить одну строку из `schema_migrations`, перезапустить —
миграция должна выполниться и зарегистрироваться заново; при намеренно
сломанном SQL — warning в логе, записи в реестре нет.

**Файлы:** `src/server/models.py`, `src/server/database.py` (новая миграция).

## Этап 5. Производительность

### Шаг 5.1 — Поиск без полной загрузки (проблема №15)

**Файлы:** `src/server/models.py`, `database.py` (миграция), `routes/catalog.py`.

**Что делать:**
1. Добавить колонку `Product.name_search` (casefold-версия `name`).
2. Миграция: создать колонку + заполнить `UPDATE products SET
   name_search = ...` (casefold в Python, батчами).
3. Записывать `name_search` при сохранении товаров (`_save_products`).
4. В `list_products` фильтр `Product.name_search LIKE '%' || :s || '%'` вместо
   загрузки всех товаров в Python. Индекс не нужен (LIKE с ведущим `%` всё
   равно сканирует), но один SQL вместо двух проходов по 5000+ строкам.

**Почему:** текущий поиск грузит все товары магазина в память и делает
повторный запрос с `IN (тысячи id)` — главное узкое место UI.

**Проверка:** поиск по кириллице работает так же (SQLite `LOWER()` не дружит
с кириллицей — поэтому casefold-колонка, а не `LOWER()`); время ответа
`GET /api/products?search=молоко` заметно падает.

### Шаг 5.2 — Проверка отмены без expire_all (проблема №16)

**Файл:** `src/server/services/catalog_scanner.py`.

**Что делать:** заменить
```python
self.db.expire_all()
job = self.db.query(ScanJob).filter(ScanJob.id == self.job_id).first()
```
на лёгкий запрос без инвалидации сессии:
```python
status = (
    self.db.query(ScanJob.status)
    .filter(ScanJob.id == self.job_id)
    .first()

if status and status[0] == "cancelled":
```

(по необходимости — `db.commit()` перед чтением, чтобы сбросить снапшот

**Почему:** `expire_all()` на каждой странице пагинации сбрасывает весь
identity map — все объекты перечитываются из БД.

**Проверка:** отмена задания (`POST /api/jobs/{id}/cancel`) во время скана
по-прежнему останавливает скан; логи без лишних SELECT'ов.
