# Design

## Context

Мотивация — `proposal.md` (Why), требования — дельты в `specs/`.

Текущее состояние, которое определяет подход:

- **`products`**: уникальность `(product_id, store_code)` реализована **отдельным** `CREATE UNIQUE INDEX uq_product_store` (миграция `add_product_indexes`). В реальной БД есть ещё устаревший уникальный индекс `uq_product_store_category (product_id, store_code, category_id)`, оставшийся от ранних версий. С новым ключом он конфликтует: один товар в одной категории у двух типов одного кода.
- **`price_history`**: уникальность — **встроенное** `CONSTRAINT uq_price_history_day UNIQUE (...)` в `CREATE TABLE`. SQLite не умеет менять такое ограничение, поэтому таблицу нужно пересобрать (~217 тыс. строк).
- **`stores.shop_type` ненадёжен**: у «Моя цена» записан 3. `Store.__init__` сейчас ставит его правильно, но старые строки испорчены.
- `init_db()` сначала выполняет `create_all`, затем все незарегистрированные миграции по порядку. На **новой** БД это означает: таблицы создаются по новой модели, а затем выполняются **все** старые миграции. Например, `add_product_indexes` выполняет `CREATE UNIQUE INDEX IF NOT EXISTS uq_product_store ON products(product_id, store_code)`, и этот индекс усилил бы старый ключ.
- Старые миграции `create_price_history` и `backfill_price_history` пишут в `price_history` без типа. На БД, где они ещё не выполнялись, а `price_history` уже создана по новой модели, вставка упадёт на `NOT NULL`.
- Окружение: Python 3.10, SQLite 3.39, SQLAlchemy 2.0. Проверено, что на «сыром» соединении pysqlite с `isolation_level=None` и явным `BEGIN IMMEDIATE` откатываются и DDL (`ALTER TABLE ... RENAME/ADD COLUMN`, `CREATE`, `DROP`), и данные.
- В API магазин адресуется только `store_code`. Правило выбора типа для сканирования уже есть: `catalog_scanner.py:resolve_store_type`.

## Goals / Non-Goals

**Goals:**
- Одинаковая схема ключей и индексов на новой и на мигрированной БД.
- Миграция атомарна: либо выполнена целиком, либо БД не изменилась.
- Одно правило разрешения типа для всех эндпоинтов чтения и один формат ссылки на магазин (`код|тип`) для наборов.

**Non-Goals:**
- Пересборка `products`: нужна только для NOT NULL на уровне БД (см. D3). Устаревшая колонка `historical_discount_percent` и её индекс тоже остаются.
- Изменение `ScanJob.store_code` и формата прогресса заданий.
- Изменение ключа категорий: они остаются универсальными.

## Decisions

### D1. Тип в записи — канонический числовой код строкой (`store_type_code`)
Колонка `store_type_code VARCHAR` в `products` и `price_history` хранит результат `resolve_store_type_code(...)` (`'1'`, `'6'`, `'9'`…). Это значение уже передаётся в API Магнита и не зависит от написания: «Магнит», «MM» и «1» дают один код.
- *Альтернатива — русское название `store_type`*: у одного типа есть несколько написаний, сравнение по строке ненадёжно.
- *Альтернатива — `stores.shop_type` (INTEGER)*: значения в БД испорчены, а тип пришлось бы приводить между INTEGER и строкой кода API.

Сканер вычисляет `self.store_type_code = resolve_store_type_code(self.store_type)` один раз в конструкторе. Все чтения, записи и фильтры по `Product`/`PriceHistory` в `_save_products`, `_upsert_price_history`, `_mark_missing_products` и `cleanup_stale_products` идут по паре (`store_code`, `store_type_code`). `cleanup_price_history` остаётся глобальной.

### D2. Уникальные ключи — именованные уникальные индексы с новыми именами
В модели `UniqueConstraint` заменяется на `Index(..., unique=True)`: `uq_product_store_type (product_id, store_code, store_type_code)` и `uq_price_history_store_type_day (product_id, store_code, store_type_code, scan_date)`. Тогда `create_all` и миграция дают одинаковые именованные индексы, как уже сделано для `uq_store_code_type`.

Имена новые, чтобы не совпасть с `uq_product_store`, который `add_product_indexes` создаёт на новой БД. Новая миграция **всегда** удаляет устаревшие индексы (`DROP INDEX IF EXISTS uq_product_store`, `uq_product_store_category`), в том числе на новой БД.

У неуникальных индексов (`ix_product_store_lookup`, `ix_product_price_change`, `ix_product_last_scan`, `ix_price_history_lookup`) имена сохраняются, а состав получает `store_type_code` после `store_code`. Миграция пересоздаёт их, если состав старый. Поэтому `CREATE INDEX IF NOT EXISTS` в старых миграциях на новой БД ничего не ломает: индекс с этим именем уже есть, и миграция его пропускает.

### D3. `products`: `ADD COLUMN` + заполнение без пересборки
`ALTER TABLE products ADD COLUMN store_type_code VARCHAR`, затем заполнение (D5) и проверка, что `NULL` не осталось (иначе исключение и откат). После этого — замена индексов (D2). В модели колонка `nullable=False`: на новой БД NOT NULL действует на уровне схемы, на мигрированной его обеспечивает ORM. Все записи идут через `_save_products`.
- *Альтернатива — `NOT NULL DEFAULT '1'`*: молча записала бы «Магнит» в любую запись без типа и скрыла бы ошибку. Отклонено.
- *Альтернатива — пересборка `products`*: 40+ колонок, устаревшие колонки и индексы. Риск выше, а выигрыш — только NOT NULL на уровне БД.

### D4. `price_history`: пересборка в одной транзакции
На одном «сыром» DBAPI-соединении (`engine.raw_connection()`, `isolation_level=None`) выполняются `BEGIN IMMEDIATE`, все шаги и `COMMIT`; при любой ошибке — `ROLLBACK` и исключение (контракт `_run_migration`). В эту же транзакцию входит D3 — так выполняется требование «при ошибке БД в прежнем состоянии».

Шаги:
1. `ALTER TABLE price_history RENAME TO price_history_old`.
2. Удалить явные индексы старой таблицы (имена индексов в SQLite глобальны).
3. Создать новую таблицу по DDL модели (`CreateTable`/`CreateIndex` от `PriceHistory.__table__`, выполненные на этом соединении).
4. `INSERT INTO price_history (..., store_type_code) SELECT ..., <тип из D5> FROM price_history_old`.
5. Сверить число строк.
6. `DROP TABLE price_history_old`.

Шаги D3 и D4 пропускаются, если колонка уже есть (новая БД или повтор после частично ручного вмешательства). Удаление устаревших индексов (D2) выполняется всегда.

### D5. Источник типа для существующих записей
Карта `store_code → код типа` строится из `stores`: `resolve_store_type_code(store_type)` по каждому коду. Если у кода несколько магазинов, берётся самый ранний (`created_at`, затем `rowid`, как в `add_store_code_type_unique`) и в лог пишется предупреждение. Карта кладётся во временную таблицу (`CREATE TEMP TABLE`), заполнение идёт через `LEFT JOIN ... COALESCE(map.code, '<код DEFAULT_STORE_TYPE>')`, поэтому коды без магазина получают «Магнит».

Та же функция построения карты используется в исправленных `create_price_history` и `backfill_price_history`. В ключ дедупликации `backfill` добавляется тип, а `db.query(PriceHistory).count()` заменяется на `count(PriceHistory.id)` (правило «не запрашивать всю сущность»).

### D6. Разрешение типа при чтении отличается от сканирования
Новая функция рядом с `resolve_store_type` — `resolve_store_type_filter(db, store_code, store_type) -> Optional[str]`:
- явный тип → его код;
- единственный магазин с кодом → код его типа;
- несколько магазинов → `AmbiguousStoreError`;
- магазина нет → `None`, без фильтра.

Отличие от сканирования (там без магазина берётся тип из конфигурации) намеренное. Чтению нужно отдать то, что есть в БД, и не зависеть от `STORE_TYPE` в окружении. Скану нужен конкретный тип для запроса к API.

Нераспознанное значение `store_type` должно давать 400, а `resolve_store_type_code` подставляет тип по умолчанию. Поэтому в `constants.py` выделяется строгий разбор `parse_store_type_code(value) -> str` с `ValueError` для неизвестного значения. `resolve_store_type_code` использует его и сохраняет прежний запасной вариант.

Роуты переводят `AmbiguousStoreError` и `ValueError` в 400 через общий помощник по образцу `_resolve_store_type_or_400`.

### D7. Ссылка на магазин в наборах: `код|тип`
Элементы `store_codes` разбираются в пары (код, `store_type` или `None`) и разрешаются по D6. Разделитель `|` не встречается ни в кодах (цифры), ни в типах. В `multi-prices` ключом ответа служит **исходный** элемент запроса, поэтому при прежнем формате (`992104,210117`) структура ответа не меняется. Статистика по набору фильтруется через `OR` по парам (`store_code = ? AND store_type_code = ?`) или по одному коду для элементов без фильтра типа.
- *Альтернатива — отдельный параметр `store_types` параллельным списком*: хрупкое сопоставление по позиции. Отклонено.

`ProductFilters` получает `store_type_code: Optional[str]`, а `get_products_stats` принимает список пар.

### D8. Поля ответов
- `product_to_list_item`, ответ `GET /api/products/{id}` и `/history` дополняются `store_type_code`, схема `ProductListItem` — тоже.
- `StoreResponse` получает `store_type_code` как вычисляемое поле Pydantic (`computed_field` от `store_type`): по конвенции модели не содержат логики.
- `multi-prices` отдаёт `shop_type = int(p.store_type_code)` по записи товара, а не по `stores`. Это сразу исправляет ссылки (`product-links`) независимо от D9.

### D9. Исправление `stores.shop_type`
Отдельная миграция `fix_store_shop_type` (после `add_product_store_type`) выставляет `shop_type = STORE_TYPE_CODES[store_type]` для всех магазинов. Если `store_type` не распознан, значение не трогается, а в лог пишется предупреждение. Миграция отдельная, потому что независима от ключа товаров и может выполниться, даже если тяжёлая миграция упала.

### D10. Фронтенд: ключ магазина `код|тип` и совместимость `localStorage`
В `base.html` появляются общие помощники:
- `storeRef(code, typeCode)`;
- `parseStoreRef(ref)`;
- `normalizeStoreRefs(saved, stores)` — переводит сохранённые элементы без типа в `код|тип`, если код однозначен, а при неоднозначном коде берёт первый магазин по порядку списка.

В `products.html` ключом выбора (`compareStores`), колонок, `productMap` и запросов `multi-prices`/`stats` становится ref. Идентификаторы DOM строятся как `код-тип`.

Позиции списка покупок получают `store_type_code`. Старые позиции без него запрашиваются по одному коду: при уникальных кодах бэкенд разрешит его сам (D6). Группировка в `shopping_list.html` идёт по ref.

## Risks / Trade-offs

- [Необратимое изменение схемы при первом старте] → Перед первым стартом нужна резервная копия `magnit.db` (Migration Plan). Перед применением миграция проверяется на копии реальной БД.
- [NOT NULL на мигрированной БД обеспечивает только ORM] → Единственный путь записи — `_save_products`. Проверка задачи — `SELECT COUNT(*) WHERE store_type_code IS NULL` = 0 после скана.
- [Устаревшие миграции на новой БД создают индексы старого ключа] → Новая миграция всегда удаляет устаревшие уникальные индексы. Проверка — старт на пустой БД и `PRAGMA index_list`.
- [Тип у кода с несколькими магазинами при миграции угадывается] → Сейчас таких кодов нет. Выбирается самый ранний магазин, выбор пишется в лог. Ошибочно отнесённые записи исправит ближайший скан каждого магазина.
- [Внешние клиенты API получают 400 при неоднозначном коде] → Возможно, только если у кода появится второй тип. Описано в `docs/API.md`, текст ошибки называет нужный параметр.
- [Объём правок `products.html` (~3000 строк) → регрессии UI] → Ручной чек-лист в задачах: один магазин, несколько магазинов, два магазина с одним кодом на тестовой БД, старый `localStorage`.
- [Блокировка БД на время пересборки] → Миграция идёт в `init_db()` до запуска планировщика и приёма запросов. Копирование ~217 тыс. строк занимает секунды.

## Migration Plan

1. Остановить сервер и скопировать `src/data/magnit.db` вместе с `magnit.db-wal` и `magnit.db-shm`, если они есть.
2. Запустить сервер. В логе должны быть `Миграция: add_product_store_type...` и `Миграция: fix_store_shop_type...` без предупреждений, а число строк `products`/`price_history` — совпадать с прежним.
3. Откат: остановить сервер и вернуть файлы из копии. Старый код с новой схемой несовместим (ORM не знает `store_type_code`, а `uq_product_store` удалён), поэтому откат — только вместе с откатом кода.
