# Design

## Context

- Активный загрузчик страницы `/products` — `loadProductsEnhanced` (`loadProducts = loadProductsEnhanced`, products.html:2658): грузит каталог каждого выбранного магазина целиком (страницами по 1000, `limit=1000` в цикле, products.html:1943) и склеивает по `product_id`. Слияние — «первая запись побеждает»: `if (!productMap[p.product_id])` (products.html:1987), порядок магазинов = порядок `selectedStores` (порядок отмеченных строк в таблице магазинов; при выборе всех это 992104, 210093, 210117, 324679 из порядка `/api/stores`).
- Фильтр режима «Новая цена» (`showNewPriceMode`) применяется к склеенной записи: `p.price_change_percent > 0` (products.html:2169-2175). Режим «Последнее изменение» (чекбокс выключен) фильтра не применяет, а только иначе считает отображаемый процент (`renderProductRow`, products.html:1204-1239).
- Цены и ↓/↑% в колонках магазинов берутся из `/api/products/multi-prices` (products.html:2086) и рисуются по каждому магазину отдельно (products.html:2315-2331) — они уже корректны и не зависят от склеенной записи.
- Серверные фильтры (`search`, категории, диапазон цен, окно видимости устаревших, наличие) применяются к каждому магазину до склейки (products.html:1943-1957). По умолчанию `GET /api/products` отдаёт только товары в наличии (`in_stock=true` и `quantity > 0`) и в окне видимости (`product_query.py:build_product_query`), поэтому в обычном режиме все загруженные записи уже в наличии; записи без наличия приходят только при фильтре «Нет в наличии» (`include_out_of_stock=true`).
- Счётчики статистики запрашиваются только по первому магазину: `/api/products/stats?store_code=selectedStores[0]` (products.html:1852). Сервер (`product_query.py:get_products_stats`) считает строки (`count(*)`), а снижения — независимо от наличия.
- Номера строк `products.html` приведены по рабочей копии, включающей незакоммиченный код архивированного изменения `hide-zero-stock-prices` (`hasStock`, проверки остатка). Этот код — предпосылка изменения и коммитится до начала реализации.
- Ограничения проекта: комментарии/docstrings — русский; `docs/API.md` и `docs/USER_GUIDE.md` править в том же изменении; миграции БД не нужны.

Подробности мотивации — в proposal.md; требования — в specs/product-catalog/spec.md.

## Goals / Non-Goals

**Goals:**
- Снижение в любом выбранном магазине (при наличии товара в нём) делает строку видимой в режиме «Новая цена».
- Детерминированная атрибуция записи склейки: поля строки (цена, остаток, процент изменения) берутся из магазина-источника по правилу приоритета.
- Статистика списка (всего / в наличии / со снижением / с повышением) по набору выбранных магазинов — на API и в счётчиках страницы.
- Совместимость: одиночный `store_code`, контракты `GET /api/products` и `GET /api/products/multi-prices` не меняются.

**Non-Goals:**
- Серверная склейка и пагинация `GET /api/products` по набору магазинов: клиентские фильтры («Экономия», наличие, режим «Последнее изменение») работают по полному загруженному множеству; серверная пагинизация их сломала бы.
- Серверный параметр «только снижения» для `GET /api/products` — фильтр режима «Новая цена» остаётся клиентским над полным множеством.
- Изменение логики режима «Последнее изменение» (Branch A/B в `renderProductRow`).
- Удаление старого пути `loadProducts` / `loadMoreProductsFromAPI` / `renderProductsList()` без аргументов (мёртвый код после переопределения; отдельная чистка).
- Изменения БД, моделей, планировщика и сканера.

## Decisions

1. **Атрибуция выполняется при клиентском слиянии, а не на сервере.**
   Данные всех выбранных магазинов уже загружаются целиком, поэтому серверная склейка не даёт выигрыша в корректности, но сломала бы клиентские фильтры, оперирующие полным множеством. Рассмотрены и отклонены: (а) серверный `store_codes` + оконные функции SQL и пагинация — регрессия фильтров и лишний код; (б) оставить first-store-wins и проверять снижение по `multi-prices` только в момент рендера — фильтр наличия и счётчики уже применены к склеенной записи до загрузки `multi-prices`, расхождения сохранятся.

2. **Правило выбора записи (merge-функция) зависит от фильтра наличия.** Для каждой пары «уже накопленная запись / кандидат из следующего магазина» выигрывает запись по приоритету:
   - обычный режим: (1) `price_change_percent > 0` И в наличии (`in_stock=true` и `quantity > 0`), среди таких — наибольший процент; (2) в наличии — по порядку выбранных магазинов; (3) по порядку выбранных магазинов;
   - фильтр «Нет в наличии»: (1) не в наличии И `price_change_percent > 0`, среди таких — наибольший процент; (2) не в наличии — по порядку выбранных магазинов; (3) по порядку выбранных магазинов.

   Кандидат заменяет накопленную запись только при строго лучшей ступени или строго большем проценте в той же ступени — равенство разрешается порядком магазинов (стабильный рендер). Обычный режим согласован с позицией проекта «скидки на отсутствующий товар не показываем» (`prices.py:35-37`); в обычном режиме ступени наличия почти не срабатывают (записи без наличия не загружаются, см. Context) и правило сводится к «наибольшее снижение, иначе порядок магазинов». Режим «Нет в наличии» зеркалит ступени, иначе товар, отсутствующий в одном магазине и имеющийся в другом, получил бы запись с наличием и пропал бы из клиентского фильтра `!p.in_stock`; условие наличия в фильтре «Новая цена» при этом не применяется — как в `hasStock` для сравнения цен.
   Замена записи выполняется по индексу: `productMap` хранит позицию `product_id` в `allProducts`, и при победе кандидата элемент массива перезаписывается на месте — позиция строки определяется первой встреченной записью.
   Побочное свойство: смена приоритета меняет поля, по которым работают фильтры наличия и «Экономия» (products.html:2016-2022, 2095-2131) — это и есть требуемое поведение (фильтры отражают магазин-источник).

3. **Фильтр «Новая цена» не переносится на сервер.** Он применяется после слияния к полному множеству (страница всегда грузит каталог целиком), поэтому корректен без пагинации; серверный `only_price_decrease` избыточен.

4. **Статистика — серверная, по набору магазинов.** `GET /api/products/stats` принимает `store_codes` (CSV) в дополнение к `store_code`; все счётчики — `count(distinct product_id)` с условием: `total` — без условия, `in_stock` — `in_stock=true` и `quantity > 0` хотя бы в одном магазине, `with_price_decrease` — `price_change_percent > 0` в магазине, где товар при этом в наличии, `with_price_increase` — `price_change_percent < 0` в любом магазине. Одиночный `store_code` и вызов без магазина обрабатываются теми же выражениями.
   Следствия: для одного магазина `total`, `in_stock`, `with_price_increase` не меняются (`(product_id, store_code)` уникальна), `with_price_decrease` может уменьшиться — снижения на отсутствующих товарах больше не считаются, счётчик ближе к списку режима «Новая цена»; без магазина `total` становится числом уникальных товаров, а не строк. Повышение намеренно считается без условия наличия (вопрос в рамках изменения не ставился). Полного совпадения со списком нет: статистика не учитывает окно видимости, категории и поиск. Альтернатива «сложить клиентскую статистику по магазинам» отклонена: `total` и `in_stock` не аддитивны из-за дублей `product_id`.

5. **Слияние выносится в отдельную чистую функцию** (`mergeProductRecords(existing, candidate, preferOutOfStock)`, флаг — включён ли фильтр «Нет в наличии») в `products.html` — единая точка правила приоритета, проще проверять и править; комментарий на русском.

6. **Дополнительная метка магазина-источника у значка ↓ не добавляется:** ↓ и так отображаются внутри колонки своего магазина (products.html:2327-2331), чего достаточно для идентификации.

## Risks / Trade-offs

- [Изменение порядка строк после смены приоритета записи] → merge сохраняет позицию первой записи `product_id` (вставка не переставляется); проверить сортировки `name` / `price` / `last_seen` и группировку по категориям.
- [Фильтры наличия/«Экономия» начинают опираться на другую запись] → закрыто сценариями спецификации; вручную проверить `stockFilter` («В наличии» / «Нет в наличии» / «Мало») и `savingsFilter` на выборке из 4 магазинов.
- [Режим «Последнее изменение» читает склеенную запись] → логика Branch A/B в `renderProductRow` не меняется, но `p.price_change_percent` теперь может прийти из другого магазина; вручную проверить отображаемые проценты в этом режиме.
- [Меняются значения статистики] → `with_price_decrease` одиночного магазина может уменьшиться, `total` без магазина считает уникальные товары; поля ответа прежние, изменение описывается в `docs/API.md`.
- [Одинаковые проценты снижения в нескольких магазинах] → детерминированный разбор по порядку выбранных магазинов (стабильность между перезагрузками).
- [Агрегация статистики по ~13 тыс. строк] → используются существующие индексы `store_code`, `price_change_percent` (миграции `add_product_indexes`, `ensure_product_last_scan_index`); объём приемлем для SQLite с `busy_timeout`.
- [Кэш браузера со старым JS шаблона] → шаблон отдаётся сервером, при обновлении кода версия меняется; миграция состояния localStorage не требуется.
- [Сосуществование двух путей загрузки на странице] → старый путь не трогаем (Non-Goals); риск путаницы при будущих правках отмечен, но расширение области сейчас опаснее.

## Migration Plan

1. Предпосылка: незакоммиченный код `hide-zero-stock-prices` закоммичен (с согласия пользователя).
2. Деплой — обычный перезапуск FastAPI (шаблоны и Python-код), миграции БД не выполняются.
3. Проверка: `GET /api/products/stats?store_code=992104` возвращает прежние `total`, `in_stock`, `with_price_increase` и `with_price_decrease` не больше прежнего; `GET /api/products/stats?store_codes=992104,210117` возвращает объединение; на `/products` с 4 магазинами в режиме «Новая цена» виден товар со снижением из 210117 (Сосиски 159.99 → 119.99, ↓25%).
4. Откат: revert изменений. Параметр `store_codes` необязателен — внешние клиенты на него не полагаются, данные не менялись.
