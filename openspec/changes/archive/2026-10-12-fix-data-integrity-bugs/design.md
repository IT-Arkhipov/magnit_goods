# Design

## Context

Мотивация — см. proposal.md. Ограничения проекта, влияющие на решения:

- SQLite без принудительных FK: `Product.category_id` может указывать на несуществующую или чужую категорию, и БД этого не заметит. В таблице с `INTEGER PRIMARY KEY` после полного удаления строк новые ID снова начинаются с 1.
- Фоновые задачи открывают свою `SessionLocal()`. Статус задания меняется из разных сессий: `POST /api/jobs/{id}/cancel` пишет в одной, фоновая работа — в другой.
- Автотестов нет, проверка ручная (Swagger UI, веб-интерфейс, SQLite-клиент). `ruff check src/` должен оставаться чистым.
- Rate limiting и bulk-операции в `_save_products` не трогаем (AGENTS.md).

## Goals / Non-Goals

**Goals:**
- Минимальные локальные правки, закрывающие пункты 1–7, 14, 15 анализа.
- Один общий механизм финализации статуса задания, чтобы правило «cancelled — окончательный статус» нельзя было забыть в новом месте.

**Non-Goals:**
- Исправление уже записанных в БД неверных `last_change_date` (нет надёжного источника истины).
- Единый формат `store_type`, определение «отслеживаемых категорий», уникальность магазинов — это change `unify-store-type-and-tracking`.
- Перевод фоновой замены каталога с in-memory статуса на `ScanJob`.

## Decisions

### D1. Поиск: повторный запрос по `Product.id`, а не по `product_id`
`list_products` уже фильтрует кандидатов через `_build_filtered_query()`. Второй запрос строим по первичным ключам найденных строк (`Product.id.in_(...)`). `product_id` одинаков у одного товара во всех магазинах, поэтому фильтр по нему возвращал записи других магазинов.
*Альтернатива:* фильтровать и пагинировать прямо в Python. Отклонено: сортировку и пагинацию оставляем в SQL. Производительность поиска — отдельная задача (обзор №15).

### D2. Полная замена каталога — upsert по `magnit_id` в одной транзакции
`replace_all_categories` сначала, как и сейчас, собирает данные API по всем корневым категориям; при любой ошибке API БД не трогаем. Затем в одной транзакции:
1. Загружаем существующие категории в словарь `magnit_id → Category`.
2. Корневые категории: обновляем `name`, `parent_id=None` или создаём новую с `is_tracked=False`; `flush()` даёт PK новым строкам.
3. Подкатегории: родитель берётся по `magnit_id` корня; обновляем `name`/`parent_id` или создаём новую.
4. Категории, которых нет среди `magnit_id` из API (включая строки с `magnit_id IS NULL`), удаляем. Перед этим обнуляем `Product.category_id` у их товаров, чтобы не оставлять висячих ссылок. Сначала удаляются дети, затем корни.
5. `commit()`; при исключении — `rollback()`.

Если API вернул один `magnit_id` в нескольких местах, побеждает первое вхождение, остальные пишутся в лог (warning). Статистика: `added` — созданные, `updated` — переименованные или перенесённые, `deleted` — удалённые; `total` — число уникальных `magnit_id`.
*Альтернатива:* удалить и пересоздать, затем перепривязать товары через `old_pk → magnit_id → new_pk`. Отклонено пользователем: сложнее и ломает ссылки, хранящиеся вне БД (выбранные категории в localStorage UI).

### D3. Финализация заданий через общий хелпер
Новый модуль `src/server/services/jobs.py`:
- `finalize_job(db, job_id, status, **fields)` перечитывает задание (`db.expire_all()` + запрос). Если статус уже `cancelled`, ничего не меняет и возвращает `False`; иначе записывает `status`, `finished_at` и переданные поля.
- `mark_unfinished_jobs_failed(db)` переносит `_mark_all_running_failed_on_startup` из `routes/stores.py` и расширяет фильтр до `status IN ('pending', 'running')`.

`CatalogScanner.scan_products` при отмене возвращает нулевую статистику с ключом `"cancelled": True`. Ключ информационный: решение принимает `finalize_job`, потому что отмена может прийти и после окончания сканирования. `finalize_job` используют `prices.py:run_update`, `scheduler.update_prices_job`, `scheduler.scan_catalog_job` (обе фазы) и финал `scan_all_stores`, который сейчас проверяет отмену вручную.
*Альтернатива:* проверять статус вручную в каждом месте. Отклонено: именно так и появился баг.

### D4. Последнее изменение цены сравнивается с последней сохранённой ценой
«Реальное изменение» = текущая цена отличается от `existing.price` (цены из предыдущего скана) больше чем на 0.01. В этом случае: `last_change_price = existing.price`, `last_change_date = now`, `last_price_change = now`. Иначе три поля в `update_data` не попадают.

Почему `existing.price`, а не `prev_day_price`: цена предыдущего дня остаётся «вчерашней» весь текущий день, поэтому повторный скан в тот же день снова видел бы изменение и сдвигал дату. Сравнение с последней сохранённой ценой срабатывает ровно один раз на каждое изменение. Пример 100 → 80 → 80 → 70:

| Скан | existing.price | current | last_change_price | last_change_date |
|---|---|---|---|---|
| день N | 100 | 80 | 100 | N |
| день N+1 | 80 | 80 | 100 (без изменений) | N |
| день M | 80 | 70 | 80 | M |

Логику `previous_price` / `price_change_percent` (сравнение с ценой предыдущего дня из `price_history`) не меняем.

### D5. Товары без цены пропускаются на этапе парсинга
`MagnitAPIClient._parse_product` возвращает `None`, если цена отсутствует или ≤ 0, и пишет warning с `product_id`. Вызывающий код уже отбрасывает `None`. Так товар без цены не попадает ни в `_save_products`, ни в `price_history`.
*Альтернатива:* сохранять товар с `in_stock=False`. Отклонено: создаёт записи с ложной ценой 0.

### D6. `.env`: `load_dotenv()` при импорте `main.py` и перерегистрация заданий
- В `main.py` до чтения `os.getenv` вызываем `load_dotenv(<корень>/.env)` с `override=False`, чтобы окружение процесса имело приоритет.
- `scheduler.py`: тело `init_scheduler` разделяем на `register_jobs(store_code)` (`add_job(..., replace_existing=True)`) и запуск. `update_prices_job` больше не получает список категорий, зафиксированный при регистрации: вызывает `scan_products(category_ids=None, tracked_only=True)`, и категории читаются в момент запуска.
- `select_store`: после записи `.env` выставляет `os.environ["STORE_CODE"]` / `["STORE_TYPE"]`, вызывает `register_jobs(store.store_code)` и запускает планировщик, если он не запущен.
*Альтернатива:* `uvicorn --env-file .env`. Отклонено: зависит от способа запуска и не решает смену магазина на лету.

### D7. `clear-by-categories`
Добавляем `except HTTPException: raise` перед общим `except Exception`, по образцу `preview_stores`.

## Risks / Trade-offs

- [Старые `last_change_date` остаются «сдвинутыми»] → документировать в DEVELOPMENT.md. Значения выправятся при следующем реальном изменении цены.
- [Upsert по `magnit_id` при дублях в API теряет вторую привязку подкатегории к другому корню] → warning в логе. Раньше создавались две строки с одним `magnit_id`, из-за чего `_save_products` (`.first()`) и так привязывал товары к случайной из них.
- [Перерегистрация заданий из HTTP-потока] → `BackgroundScheduler.add_job` потокобезопасен; `replace_existing=True` исключает дубли.
- [`finalize_job` и отмена в одну и ту же миллисекунду] → гонка остаётся теоретической; итог либо `cancelled`, либо `completed`, в обоих случаях корректный.

## Migration Plan

Миграции схемы не нужны. Развёртывание — обычный перезапуск сервера. Откат — `git revert` коммита; данные остаются совместимыми, так как структура таблиц не меняется.
