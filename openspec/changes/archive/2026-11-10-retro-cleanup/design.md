# Design

## Контекст

По данным БД (2026-11-10) пользователь сканирует цены только кнопкой «Сканировать все магазины», категории обновляет только полной заменой каталога; заданий планировщика в БД нет ни одного.

## Решения

- **Одна реализация сканирования всех магазинов** — `services/store_scan.py` (`create_scan_all_stores_job`, `run_scan_all_stores`). Её вызывают роут и планировщик, поэтому плановый скан идёт по всем магазинам, с тем же прогрессом и отменой.
- **Статус полной замены каталога — в сервисе** (`catalog_updater.py`: `try_begin_catalog_update` / `run_catalog_update`). Флаг проверяется и берётся под одной блокировкой; планировщик и роут делят его, поэтому две замены не идут одновременно. Статус по-прежнему в памяти процесса.
- **Расписание**: каталог — вс 6:00, скан — ежедневно 8:00 (в воскресенье скан идёт уже по новому каталогу). Скан пропускается, если задание `scan_all_stores` уже активно.
- **Режим «Последнее изменение»** — одна функция `priceChangeForMode` в `products.html` вместо копий логики; нужное поле `last_change_price` добавлено в `multi-prices`.
- **Удаление данных магазина** — `catalog_scanner.py:delete_store_products` (код + код типа), миграция `cleanup_orphan_store_products` для накопленных записей; при пустой таблице магазинов миграция ничего не удаляет.
- **Повторы запросов** — `MagnitAPIError` несёт HTTP-код; повторяются только сетевые ошибки, 429 и 5xx.

## Риски

- Удалённые эндпоинты (`update-catalog`, `scan`, `load-from-json`, Playwright-роуты) могли вызываться вручную через Swagger — замена: `fetch-magnit-ids` и прямые ссылки.
- 4xx без повтора: если API начнёт временно отвечать 403/400, категория пропускается до следующего скана (наличие её товаров не сбрасывается).
