# Proposal

## Why

Модули по-разному понимают одни и те же понятия, поэтому поведение зависит от того, какой путь вызвал сканирование:
- тип магазина уходит в API Магнита в трёх разных форматах с тремя разными значениями по умолчанию;
- «отслеживаемые категории» в одних эндпоинтах включают корневые, в других — нет, а синхронизация подкатегорий из-за этого не выполняется никогда;
- «в наличии» считается двумя способами;
- магазины дедуплицируются по коду, хотя их идентификатор включает тип;
- провалившиеся миграции регистрируются как выполненные;
- загрузка категорий из JSON не работает с фактическим форматом файла.

Изменение сводит эти правила к одному определению каждого понятия (пункты 8–13, 16, 17 анализа 2026-10-12 и шаги 2.2, 2.3, 4.3 из `docs/PLAN_FIXES_2026-09-27.md`).

## What Changes

- **Тип магазина в запросах к API** нормализуется в одном месте: API-код (`MM`), русское название (`Магнит`) или числовой код (`1`) приводятся к числовому коду для всех запросов товаров и категорий. Значение по умолчанию одно на весь проект; захардкоженные магазин `210117` и типы `"9"`/`"6"` удаляются.
- **Rate limiting** применяется к каждому запросу каталога, включая получение подкатегорий при синхронизации категорий.
- **Отслеживаемые категории** везде означают отмеченные подкатегории: ручное и плановое обновление цен, `scan-prices`, `scan-all-stores`.
- **Синхронизация подкатегорий** (`POST /api/categories/scan`, `/update-catalog`, плановое еженедельное задание) обрабатывает все корневые категории, а не только «отслеживаемые» корни, которых UI никогда не отмечает.
- **Загрузка категорий из JSON** (`POST /api/categories/load-from-json` и алиасы) читает фактический формат `categories.json` — плоский массив `[{id, title}]`.
- **Статистика товаров** (`GET /api/products/stats`) считает «в наличии» так же, как список товаров: `in_stock` и остаток больше нуля.
- **Идентичность магазина** — пара (код, тип):
  - уникальность обеспечивается в БД;
  - создание, добавление из preview и preview дедуплицируют по паре;
  - сканирование использует тип конкретного магазина.
  - **BREAKING:** `PUT /api/stores/{id}` отклоняет изменение `store_type` и `full_address` (из них вычисляется ID).
- **Типы для поиска магазинов** (preview) задаются явным списком. **BREAKING:** неизвестный или неподдерживаемый тип даёт 400, а не молча заменяется на «все типы».
- **Сканирование всех магазинов** выполняет очистку устаревших товаров, истории цен и пометку отсутствующих товаров один раз на магазин, а не после каждой категории.
- **Миграции** регистрируются в `schema_migrations` только при успешном выполнении; неудачная миграция повторяется при следующем старте. Индекс `ix_product_last_scan`, не созданный на старых БД, создаётся новой миграцией.

## Capabilities

### New Capabilities
- `magnit-api-client`: правила обращения к API Магнита — формат типа магазина, значения по умолчанию, ограничение частоты запросов.
- `category-tracking`: какие категории считаются отслеживаемыми и как этот набор используется всеми операциями сканирования.
- `store-registry`: хранение магазинов, их идентичность и правила добавления, поиска и изменения.
- `db-migrations`: выполнение и учёт миграций схемы при старте.

### Modified Capabilities
Нет — в `openspec/specs/` пока нет спецификаций. Требования к синхронизации подкатегорий и загрузке из JSON добавляются в `category-catalog`, которую вводит изменение `fix-data-integrity-bugs`; здесь они оформлены как ADDED с собственными именами требований. Требование к статистике товаров добавляется в `product-catalog` из того же изменения.

## Impact

- `src/server/constants.py`: `resolve_store_type_code`, `DEFAULT_STORE_TYPE`, `PREVIEW_STORE_TYPES`.
- `src/server/services/magnit_api.py`, `catalog_scanner.py`, `catalog_updater.py`, `load_catalog_from_json.py`.
- `src/server/routes/catalog.py`: `scan_all_stores`, `scan_prices_in_store`, `get_products_stats`, fallback-ветки замены каталога.
- `src/server/routes/prices.py`, `src/server/scheduler.py`: набор отслеживаемых категорий.
- `src/server/routes/stores.py`, `src/server/schemas.py`, `src/server/models.py`: уникальность (code, type), валидация типов, `update_store`.
- `src/server/database.py`:
  - контракт миграций и `_run_migration`;
  - новые миграции `add_store_code_type_unique` и `ensure_product_last_scan_index`;
  - переход с `print` на `logging`.
- API:
  - `PUT /api/stores/{id}` и `POST /api/stores/preview` — **BREAKING** (см. выше);
  - `POST /api/stores` и `add-selected` — 409 / `skipped` теперь по паре (код, тип).
- Данные: дубликаты (код, тип) в `stores` схлопываются миграцией (сохраняется самая ранняя запись).
