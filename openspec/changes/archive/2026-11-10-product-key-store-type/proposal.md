# Proposal

## Why

Магазин в системе идентифицируется парой (`store_code`, `store_type`), а товары и история цен — только парой (`product_id`, `store_code`) (`models.py`: `uq_product_store`, `uq_price_history_day`). Если завести два магазина с одним кодом и разными типами (это разрешено `store-registry`), их сканы перезаписывают одни и те же строки `products`/`price_history`: цены, остатки, `previous_price` и процент изменения одного типа затирают данные другого, а UI не может их различить. Сейчас в БД коды уникальны (4 магазина), проблема скрытая — но её нужно закрыть до того, как пользователь добавит такой магазин (техдолг №1 в `docs/DEVELOPMENT.md`).

Попутно найдена связанная ошибка: `stores.shop_type` у магазина «Моя цена» (210117) равен 3 (код М.Косметик) вместо 9. `GET /api/products/multi-prices` отдаёт этот `shop_type`, и ссылки на товар в `/products` строятся с `shopType=3` — сайт Магнита открывается для чужого типа магазина.

## What Changes

- В `products` и `price_history` добавляется канонический числовой код типа магазина `store_type_code` (как в `constants.py:resolve_store_type_code`: `'1'` Магнит, `'6'` Экстра, `'9'` Моя цена…). Ключ товара — (`product_id`, `store_code`, `store_type_code`), ключ истории — (`product_id`, `store_code`, `store_type_code`, `scan_date`); индексы по магазину включают тип.
- Сканирование пишет и читает товары и историю только своего типа: цена предыдущего дня, процент изменения, пометка отсутствующих и очистка устаревших не затрагивают магазин другого типа с тем же кодом.
- Эндпоинты товаров и цен (`GET /api/products`, `/stats`, `/multi-prices`, `/{product_id}`, `/{product_id}/history`, `DELETE /api/products/clear-by-store`, `GET /api/prices/decreased`) принимают необязательный `store_type`; наборы магазинов (`store_codes`) принимают элементы вида `код` или `код|тип`. Правило разрешения типа единое: явный тип → тип единственного магазина с этим кодом → **400**, если магазинов с кодом несколько → без фильтра по типу, если магазина с кодом нет в БД. Запросы с одним кодом при уникальных кодах работают как раньше.
- Ответы с товарами и историей получают поле `store_type_code`; `GET /api/stores` — поле `store_type_code`. `multi-prices` отдаёт `shop_type` по типу самой записи товара, а не из `stores`.
- Миграция (16-я, `add_product_store_type`): добавляет колонку, заполняет её по `stores.store_type` (через `resolve_store_type_code`, не по ненадёжному `shop_type`), пересобирает `price_history` (её уникальное ограничение встроено в таблицу), заменяет уникальные индексы `products`, включая устаревший `uq_product_store_category`. Товары кодов, которых нет в `stores` (сейчас 818080, 1831 товар), получают тип по умолчанию.
- Миграция (17-я, `fix_store_shop_type`): пересчитывает `stores.shop_type` по `store_type`.
- UI `/products` и список покупок (`shopping_list.html`, `base.html`) различают магазины по паре «код|тип»: выбор магазинов, колонки сравнения, история цен, «Сравнить по магазинам», ссылки на товар, проверка наличия списка покупок. Сохранённые в `localStorage` старые значения (только код) продолжают работать и переводятся на новый формат при загрузке.
- **BREAKING (только при неуникальных кодах):** запрос товаров/цен по коду, у которого в БД несколько типов, без `store_type` возвращает 400 вместо смешанных данных.

## Capabilities

### New Capabilities

_(нет)_

### Modified Capabilities

- `product-catalog`: товары адресуются магазином (код, тип); правила разрешения `store_type` и формата элементов набора магазинов в API; поле `store_type_code` в ответах; UI различает магазины с одним кодом.
- `price-tracking`: история цен и расчёт изменения цены ведутся отдельно для каждого типа магазина с одним кодом.
- `db-migrations`: индексы схемы товаров включают тип магазина; требование к миграции ключа (заполнение типа, сохранение данных, устаревшие индексы).
- `store-registry`: `shop_type` согласован с `store_type`; ответ магазинов содержит канонический код типа.
- `product-links`: ссылка на товар использует тип того магазина, чья цена показана.

## Impact

- Код: `models.py` (колонки, ключи, индексы), `database.py` (две миграции; старые миграции, пишущие в `price_history`, заполняют тип), `services/catalog_scanner.py` (`_save_products`, `_upsert_price_history`, `_mark_missing_products`, `cleanup_stale_products`), `services/product_query.py` (фильтры и статистика по магазинам с типом), `routes/catalog.py`, `routes/prices.py`, `routes/stores.py`, `schemas.py`, шаблоны `products.html`, `shopping_list.html`, `base.html`.
- API: новые необязательные параметры и поля ответов; при уникальных кодах контракт обратно совместим.
- БД: изменение схемы `products` и пересборка `price_history` (~13,3 тыс. и ~217 тыс. строк) при первом старте; откат — только из резервной копии `magnit.db`.
- Документация (в том же изменении): `AGENTS.md`, `docs/DATABASE.md`, `docs/API.md`, `docs/SERVICES.md`, `docs/DEVELOPMENT.md` (закрыть техдолг №1), `docs/USER_GUIDE.md` при изменении поведения UI.
- Вне объёма: перенос ключа товаров на `Store.id`, удаление товаров при удалении магазина, очистка «осиротевших» товаров кодов без магазина.
