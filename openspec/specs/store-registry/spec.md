# store-registry Specification

## Purpose
Определяет хранение магазинов Магнита в системе: идентичность магазина по паре (код, тип), правила добавления вручную и из результатов поиска, допустимые изменения и согласованность производных полей.

## Requirements

### Requirement: Магазин идентифицируется парой код и тип
В системе SHALL существовать не более одного магазина с данной парой (`store_code`, `store_type`). Магазины с одинаковым кодом и разными типами SHALL храниться как разные магазины.

#### Scenario: Ручное добавление дубликата
- **WHEN** магазин (`992104`, `Магнит`) уже есть, и клиент вызывает `POST /api/stores` с той же парой
- **THEN** ответ — 409, новый магазин не создаётся

#### Scenario: Тот же код, другой тип
- **WHEN** магазин (`992104`, `Магнит`) уже есть, и клиент добавляет (`992104`, `Экстра`)
- **THEN** магазин создаётся

### Requirement: Preview и добавление выбранных учитывают пару код и тип
`POST /api/stores/preview` SHALL помечать `exists_in_db` и дедуплицировать результаты по паре (код, тип). `POST /api/stores/add-selected` SHALL пропускать только магазины, пара которых уже есть в БД.

#### Scenario: Добавление из preview
- **WHEN** в БД есть (`100`, `Магнит`), и выбраны (`100`, `Магнит`) и (`100`, `Моя цена`)
- **THEN** ответ — `{"added": 1, "skipped": 1}`

### Requirement: Поиск магазинов принимает только поддерживаемые типы
`POST /api/stores/preview` SHALL принимать типы магазинов только из списка поддерживаемых для поиска (Магнит, Мини, Семейный, Экстра, Моя цена, М.Косметик) и SHALL возвращать 400 с перечнем неподдерживаемых значений, если хотя бы один переданный тип не поддерживается.

#### Scenario: Неподдерживаемый тип
- **WHEN** клиент передаёт `store_types: ["Магнит", "Заряд"]`
- **THEN** ответ — 400 с указанием `Заряд`, запрос к API Магнита не выполняется

### Requirement: Ключевые поля магазина неизменяемы
`PUT /api/stores/{id}` SHALL отклонять с ответом 400 запрос, который меняет `store_type` или `full_address` на значение, отличное от текущего. Изменение остальных полей SHALL выполняться как прежде.

#### Scenario: Попытка сменить тип
- **WHEN** клиент отправляет `PUT /api/stores/{id}` с другим `store_type`
- **THEN** ответ — 400, магазин не изменён

#### Scenario: Смена названия
- **WHEN** клиент отправляет `PUT /api/stores/{id}` с новым `name`
- **THEN** название обновлено, `id` и `shop_type` прежние

### Requirement: Сканирование использует тип выбранного магазина
Сканирование товаров для магазина SHALL выполняться с типом именно этого магазина. Если существует несколько магазинов с одним кодом, система SHALL NOT подставлять тип произвольного из них.

#### Scenario: Два магазина с одним кодом
- **WHEN** в БД есть (`100`, `Магнит`) и (`100`, `Экстра`), и выполняется сканирование всех магазинов
- **THEN** для каждого из них запросы к API передают его собственный тип

### Requirement: Числовой код типа магазина согласован с названием типа
`shop_type` каждого магазина SHALL совпадать с числовым кодом его `store_type` по справочнику типов (Магнит — 1, Мини — 2, М.Косметик — 3, Семейный — 5, Экстра — 6, Опт — 7, Заряд — 8, Моя цена — 9), в том числе у магазинов, сохранённых до этого изменения.

#### Scenario: Ранее сохранённый магазин с неверным кодом
- **WHEN** в БД магазин 210117 с `store_type` «Моя цена» и `shop_type` 3, и сервер стартует
- **THEN** после старта `shop_type` магазина равен 9

#### Scenario: Новый магазин
- **WHEN** клиент добавляет магазин с `store_type` «Экстра»
- **THEN** его `shop_type` равен 6

### Requirement: Ответ магазинов содержит код типа
Каждый магазин в ответах `/api/stores` (список, поиск, по `id`, по коду, создание, изменение) SHALL содержать поле `store_type_code` — числовой код типа магазина в виде строки, тот же, что в записях его товаров.

#### Scenario: Код типа в списке магазинов
- **WHEN** клиент вызывает `GET /api/stores`
- **THEN** у магазина с `store_type` «Моя цена» `store_type_code` равен `"9"`

### Requirement: Удаление магазина удаляет его товары
`DELETE /api/stores/{store_id}` и `POST /api/stores/delete-batch` SHALL удалять вместе с магазином его товары и историю цен (пара код и тип магазина); данные магазина другого типа с тем же кодом SHALL сохраняться. Товары и история магазинов, которых нет в `stores`, SHALL удаляться один раз миграцией `cleanup_orphan_store_products`.

#### Scenario: Удаление магазина
- **WHEN** удаляется магазин (`210117`, `Моя цена`)
- **THEN** товаров и истории цен с `store_code=210117`, `store_type_code=9` не остаётся
