# db-migrations Specification

## Purpose
Определяет, как сервер при старте применяет миграции схемы SQLite и ведёт их учёт, чтобы каждая миграция была применена полностью ровно один раз, а частичные сбои не фиксировались как успех.

## Requirements

### Requirement: Миграция регистрируется только при успехе
Миграция SHALL записываться в реестр выполненных миграций только после успешного выполнения. Если миграция завершилась ошибкой, сервер SHALL записать предупреждение в лог, продолжить старт и повторить её при следующем запуске.

#### Scenario: Сбой миграции
- **WHEN** при старте миграция завершается ошибкой
- **THEN** в логе есть предупреждение с именем миграции, в реестре её нет, сервер продолжает работу

#### Scenario: Повтор после исправления
- **WHEN** при следующем старте причина ошибки устранена
- **THEN** миграция выполняется и регистрируется

### Requirement: Выполненная миграция не повторяется
Миграция, уже записанная в реестре, SHALL пропускаться при последующих стартах.

#### Scenario: Повторный старт
- **WHEN** сервер перезапускается без изменений в БД
- **THEN** ни одна зарегистрированная миграция не выполняется повторно

### Requirement: Индексы схемы присутствуют на старых базах
После старта сервера на любой ранее созданной БД SHALL существовать все индексы, объявленные моделью товаров и истории цен, включая индекс по (`store_code`, тип магазина, `last_scan_found`) и уникальные индексы товара по (`product_id`, `store_code`, тип магазина) и истории по (`product_id`, `store_code`, тип магазина, `scan_date`), и уникальный индекс магазинов по (`store_code`, `store_type`). Устаревшие уникальные индексы товаров без типа магазина SHALL отсутствовать.

#### Scenario: Старая база без индекса
- **WHEN** сервер стартует на БД, где индекс `ix_product_last_scan` отсутствует
- **THEN** после старта индекс существует

#### Scenario: Дубликаты магазинов в старой базе
- **WHEN** в старой БД есть несколько магазинов с одинаковой парой (код, тип)
- **THEN** после старта остаётся самая ранняя запись, удаление остальных зафиксировано в логе, уникальный индекс создан

#### Scenario: Устаревший уникальный индекс товаров
- **WHEN** в БД есть уникальные индексы товаров по (`product_id`, `store_code`) или (`product_id`, `store_code`, `category_id`)
- **THEN** после старта их нет, и два магазина с одним кодом и разными типами могут хранить один и тот же товар

### Requirement: Миграция ключа товара сохраняет данные
Миграция, добавляющая тип магазина в товары и историю цен, SHALL сохранить все существующие записи `products` и `price_history` с прежними значениями полей. Если миграция завершилась ошибкой, БД SHALL остаться в состоянии до миграции.

#### Scenario: Число записей после миграции
- **WHEN** до миграции в БД 13 293 товара и 217 294 записи истории
- **THEN** после миграции их столько же, у каждой записи заполнен тип магазина

#### Scenario: Сбой посреди миграции
- **WHEN** миграция прерывается ошибкой после начала изменения таблиц
- **THEN** таблицы `products` и `price_history` имеют прежнюю схему и данные, миграция не зарегистрирована и повторится при следующем старте

### Requirement: Тип существующих записей берётся из магазина
При миграции тип магазина записи SHALL определяться по названию типа (`store_type`) магазина с тем же кодом. Для кода, которого нет среди магазинов, SHALL использоваться тип по умолчанию («Магнит»). Для кода с несколькими магазинами SHALL использоваться тип самого раннего из них, а выбор SHALL фиксироваться в логе.

#### Scenario: Магазин «Моя цена» с неверным shop_type
- **WHEN** у магазина 210117 `store_type` = «Моя цена», а `shop_type` = 3
- **THEN** его товары и история получают код типа `"9"`

#### Scenario: Товары удалённого магазина
- **WHEN** у кода 818080 есть товары, а магазина с этим кодом нет
- **THEN** его записи получают код типа `"1"` и остаются доступны по `store_code=818080`
